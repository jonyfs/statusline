# Design: Two official spec tracks, and a scaffold that cannot lie

Generated by /office-hours on 2026-09-23

## Problem Statement

Spec-driven development is broken in this repository right now, not drifting toward broken.
`bash .specify/scripts/bash/check-prerequisites.sh --json` exits with
`ERROR: plan.md not found in <repo>/specs/021-agent-rows`.
`.specify/feature.json` pins the current feature to `specs/021-agent-rows`, and that
directory holds only `spec.md` and `checklists/`. Every speckit command that calls
check-prerequisites (tasks, implement, analyze, checklist) fails on its first call.

A second pointer disagrees with the first. The `<!-- SPECKIT START -->` block in
`CLAUDE.md` names `specs/019-explaining-a-segment/plan.md`, while `feature.json` names 021.
The two diverged because `update-agent-context.sh` was not run as the work moved on. That
is a missed step, not proof of anything larger on its own.

The larger claim rests on different evidence: four of the last five features shipped with
`spec.md` alone. 017-line-legibility, 018-readme-current, 020-links-that-belong-here and
021-agent-rows have no `plan.md` and no `tasks.md`. 019-explaining-a-segment is the
exception and carries the full set: `plan.md`, `tasks.md`, `research.md`, `data-model.md`
and `quickstart.md`. Specs 001 through 016 all carry plan and tasks. So the practice
changed somewhere around 017, and `.specify/workflows/speckit/workflow.yml` still
describes only the older practice.

Two more loose ends. Commit scopes `(022)` and `(023)` appear in the log with no matching
directory under `specs/`. And `specs/003-status-change-animations` has 22 tasks checked
and 16 open, with no record of whether it was finished, cut, or forgotten.

## What Makes This Cool

The repository already refuses to let documentation lie about the code. Principle VIII
forces README images to be generated by the real renderer, and CI fails if regenerating
them produces a diff. The same idea has never been pointed at the process itself. Doing
that closes the loop: the scaffold that describes how work gets done becomes as
falsifiable as the screenshots.

## Constraints

- Principle VI: all code, comments and documentation in English. This document and every
  artifact it proposes are written in English for that reason.
- Principle IX: CI runs on Linux, macOS and Windows across Node 18, 20 and 22. Anything
  added to `scripts/smoke-test.js` runs nine times, so a check that reads git history has
  to be cheap and deterministic or it does not belong there.
- There is no PowerShell counterpart to `check-prerequisites.sh`. The only `.ps1` in the
  tree is `.specify/extensions/agent-context/scripts/powershell/update-agent-context.ps1`,
  so the track change touches bash only.
- The renderer budget and test suite stay untouched. This work adds no runtime code.
- The constitution is at version 6.0.0 and 39 KB. Amending it is deliberate work with its
  own version bump, so exactly one amendment is scheduled here and everything else stays
  an open question.

## Premises

Confirmed by the user, each tied to a command or a file rather than an impression.

1. Speckit is broken now. `check-prerequisites.sh` exits with an error because
   `feature.json` points at a directory without `plan.md`.
2. The renderer is not the main debt. 489 tests pass; subprocesses carry `timeout` and
   `windowsHide`; the cache writes through a temp file and `renameSync`; there are
   dedicated tests for malformed payloads, control characters and platform behavior.
3. The real flow is spec-then-implement. Four of the last five features shipped with
   `spec.md` only. The documented full cycle describes a process that is mostly not in use.
4. The real distribution channel is `git clone` and `git pull`. Principle XI and
   `release.yml` say releases are tag-driven; the last tag is `v1.2.7` while
   `package.json` reads `1.18.0`, and `@jonfys/statusline` returns 404 on npm.

## Approaches Considered

### Approach A: Unstick and move on
Repoint `feature.json`, regenerate the `CLAUDE.md` block, resolve spec 003. Small, low
risk, and nothing in the repository detects the same drift returning. Rejected as the
whole answer, kept as the first half hour of the chosen approach.

### Approach B: A guard rail in CI
Approach A plus a test that fails when the scaffold lies. Rejected on its own because the
test cannot be written until "valid spec" has a definition, and under any definition
`workflow.yml` supports today, four of the last five features would fail it.

## Recommended Approach

Approach C: two official tracks, with the guard rail validating the track each spec
declares.

Chosen over B because B's gate is unwritable without C's definition, and over A because A
leaves nothing behind that notices the next drift. It begins by doing A.

### The declaration

Every `spec.md` opens with YAML front matter, and this is the only place a track is
declared. Both `check-prerequisites.sh` and the new test parse this same form:

```yaml
---
track: quick
status: active
---
```

- `track` is `quick` or `full`, lowercase, exact match. `quick` means `spec.md` is the
  complete artifact set. `full` means `spec.md`, `plan.md` and `tasks.md`.
- `status` is `active`, `done` or `abandoned`. Artifact requirements are enforced only at
  `done`, so a `full` spec is allowed to exist without its plan while it is being written,
  and an `abandoned` spec is never checked for artifacts at all.
- A missing front matter block, a missing key, or an unrecognized value is a hard error,
  exit 1, naming the offending key and its allowed values:
  `ERROR: spec <dir>/spec.md declares no valid track (expected quick|full)` or
  `ERROR: spec <dir>/spec.md declares no valid status (expected active|done|abandoned)`.
  `check-prerequisites.sh` and the scaffold test emit the same text.
- The template seeds `track: quick` and `status: active` into every new spec, so a spec
  created by `/speckit-specify` is already declared. Nothing in the tooling guesses a
  track for a spec that lacks one; the seeding happens at creation, in a file the author
  is editing anyway. What stops a `full` feature from shipping mis-declared as `quick` is
  the same thing that stops any wrong spec from shipping: the author reads what they
  wrote. The test catches an absent declaration, not a dishonest one.

### The bash callers that assume plan.md

`.specify/scripts/bash/check-prerequisites.sh`, `common.sh` and `setup-tasks.sh` all
reference `plan.md`. Step 3 below updates those three. `setup-plan.sh` is unaffected: it
creates the plan rather than requiring one. The agent-context scripts in both bash and
PowerShell read `plan.md` only to summarize it, so they keep working when the file is
absent, and they are out of scope.

## Next Steps

Sizing is CC time. Dependencies are listed where the order matters.

1. Unblock, about 10 minutes, no dependencies. Decide what `specs/021-agent-rows` is.
   Commit `d4872c0` implements it, so the expected outcome is that 021 is done and
   `feature.json` should point somewhere else. Writing a plan for 021 is the wrong repair:
   step 4 would immediately mark that same directory `quick`. Then run
   `.specify/extensions/agent-context/scripts/bash/update-agent-context.sh` so the
   `CLAUDE.md` block and `feature.json` agree again.
2. Add the front matter to the template, about 15 minutes, no dependencies. Put `track`
   and `status` in `.specify/templates/spec-template.md` with one paragraph on choosing,
   and set the template default to `track: quick` and `status: active`. Quick is the
   default because it describes four of the last five features.
3. Teach the three bash callers, about 45 minutes, depends on 2 and 4, and lands in the
   same commit as 4. `check-prerequisites.sh`,
   `common.sh` and `setup-tasks.sh` read the front matter and require only what the
   declared track promises at the declared status, with the error contract above.
4. Backfill declarations, not plans, about 20 minutes, depends on 2. This lands with
   step 3 in one commit: enforcement must never arrive before the declarations it
   enforces, or every existing spec fails the new error at once. Every one of the 21
   directories under `specs/` gets front matter. The values are already determined by what
   is on disk: 001 through 016 and 019 are `full`, and 017, 018, 020 and 021 are `quick`.
   All are `done` except 003, which gets `status: active` as its interim value so
   assertion 2 stays green until step 5 decides its fate. No retroactive plan writing.
5. Resolve spec 003, size unknown until you decide, depends on nothing. 16 open tasks with
   no status. Finish it, cut it, or set `status: abandoned` with the reason in the spec
   body. Any of the three is better than leaving it undecided. Its size is the one number
   this plan cannot estimate, because only you know whether those 16 tasks still matter.
6. Decide the commit-scope convention, about 15 minutes, no dependencies. Scopes `(022)`
   and `(023)` have no directory. Either those numbers name real work that deserves a spec,
   or commit scopes are a separate sequence and should stop wearing three-digit spec
   numbers. This decision gates assertion 4 below.
7. Add the scaffold test, about 1 hour, depends on 2, 3, 4 and 6. A Node script under
   `scripts/tests/`, joined to `scripts/smoke-test.js`. Four assertions:
   1. `feature.json` names a directory that exists and satisfies its declared track at its
      declared status.
   2. Every directory under `specs/` declares a valid `track` and `status`.
   3. The `<!-- SPECKIT START -->` pointer in `CLAUDE.md` names the same feature as
      `feature.json`. This is the Principle VIII idea applied to the scaffold: the two
      pointers cannot silently disagree again.
   4. Every `(NNN)` commit scope maps to a directory that exists. This assertion reads git
      history, so it is bounded: only commits after a baseline commit recorded in the test
      are checked, everything before it is grandfathered, and it is skipped when the
      checkout is shallow (`git rev-parse --is-shallow-repository` returns true) rather
      than failing. Assertions 1 through 3 read files only and run in every matrix cell.
8. Amend the constitution, about 30 minutes, depends on 3 and 7. One new principle
   defining the two tracks and the front matter contract, with its own version bump.
   Principle XI is deliberately not touched here; see Open Questions.

Steps 1 through 4 and 6 through 8 sum to about three and a quarter hours of CC time.
Step 5 is unsized. The "two-day" figure this option carried when you chose it was human
calendar time: three hours of CC work, plus your decisions on steps 5 and 6, plus the
review that a constitution amendment deserves.

## Success Criteria

- `bash .specify/scripts/bash/check-prerequisites.sh --json` exits 0 on `main`.
- A spec created by `/speckit-specify` inherits `track: quick` and `status: active` from
  the template and clears prerequisites with no manual repair. Step 2 is what makes this
  true; no change to the specify command itself is required.
- The scaffold test passes on `main` and fails on a deliberately broken `feature.json`, a
  spec with no track, and a `CLAUDE.md` pointer edited to name a different feature.
- After step 6, commit scopes and `ls specs/` agree from the baseline commit forward.

## Open Questions

- Principle XI: resume tagging, or rewrite the principle around merge-and-pull? These are
  opposite repairs and only one can be right. This needs its own decision and its own
  amendment; step 8 does not touch it.
- Do commit scopes `(022)` and `(023)` name work that deserves a spec directory? Step 6
  turns this into a decision rather than leaving it open, but the answer is yours.

Adjacent context, not work arising from this design: `package.json` carries
`publishConfig.access: public`, `bin`, `files` and keywords for a package that has never
been published. Recorded here so it is not lost, not assigned.

## Distribution Plan

Unchanged by this work. Users install with
`git clone https://github.com/jonyfs/statusline.git ~/.claude/statusline-plugin` and
update with `git pull`, which is what README documents and what Principle IV requires.
`release.yml` fires only on `v*.*.*` tags and has not fired since `v1.2.7`, 16 versions
ago. That contradiction is left as an open question rather than repaired here.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — completeness

**Problem**

> The Problem Statement names `.specify/workflows/speckit/workflow.yml` as part of the broken scaffold ('still describes only the older practice'), but no step in Next Steps updates it. After all eight steps ship, the workflow file still declares a single full cycle while the template, the bash callers, the backfilled specs and the new test all recognize two tracks, so the scaffold still lies about the process in the one file the document cites as describing it.

**Remedy**

> Add a step that updates `workflow.yml` to describe both tracks (or state explicitly why it is left alone and what it will say after this work), and say whether the scaffold test asserts anything about it.

### R2-2 — completeness

**Problem**

> `status` gates all enforcement ('Artifact requirements are enforced only at `done`'), but nothing defines who flips a spec from `active` to `done`, or when. No step, script or assertion touches the transition. A `full` spec left at `active` indefinitely satisfies assertion 1 and check-prerequisites while carrying neither plan.md nor tasks.md, which makes the guard rail opt-in and silently bypassable by the same omission the design exists to catch.

**Remedy**

> Define the transition: which action sets `status: done` (a step in the implement flow, a manual edit at merge time, or a script), and whether anything verifies that a feature merged to main is not left `active`.

### R2-3 — completeness

**Problem**

> Step 1 concludes that 021 is done and that 'feature.json should point somewhere else' without naming the target. By step 4's own backfill every directory except 003 is `done`, so there is no in-progress feature to point at, and the document never says whether feature.json may name a `done` spec, must name 003, or supports an empty/none value. Assertion 1 and the criterion 'check-prerequisites.sh --json exits 0 on main' both depend on that unstated value.

**Remedy**

> State what feature.json holds after step 1 - a specific directory, or a defined 'no active feature' representation - and define how check-prerequisites and assertion 1 behave for that value.

### R2-4 — completeness

**Problem**

> Step 4 backfills every directory and says 'All are `done` except 003' without saying what status 003 receives. Step 5, which would decide 003, has no dependents, while step 7 (the test, whose assertion 2 requires every directory to declare a valid track and status) depends on 2, 3, 4 and 6 only. The test can therefore land while 003's declaration is still undetermined.

**Remedy**

> Name the value step 4 writes into 003 as its interim declaration, and either make step 7 depend on step 5 or state that the interim value keeps assertion 2 green until step 5 concludes.

### R2-5 — completeness

**Problem**

> Assertion 2 checks only that each directory declares a valid track and status; assertion 1 is the sole assertion that compares declaration against contents, and it applies to the single directory feature.json names. A spec declaring `full` and `done` with no plan.md, or `quick` and `done` while carrying a plan and tasks, passes the whole test suite. The title claim - a scaffold that cannot lie - is not enforced for any directory but the current one.

**Remedy**

> Either extend assertion 2 to verify that every `done` directory's artifacts match its declared track, or state deliberately that historical directories are declaration-only and say why the contents check is limited to the current feature.

### R2-6 — consistency

**Problem**

> Step 5 offers 'mark it `status: abandoned` with the reason', but The declaration defines `status` as '`active` or `done`' and rules that 'an unrecognized value is a hard error: exit 1'. Taking step 5's third option would make specs/003 fail check-prerequisites and assertion 2 the moment step 3 and step 7 land.

**Remedy**

> Either add `abandoned` to the status enum (and define what artifacts it requires and how the test treats it), or replace step 5's third option with a value the contract allows.

### R2-7 — consistency

**Problem**

> The declaration states 'There is no default. A spec that does not say is a spec that gets fixed, not guessed at', while step 2 sets 'the template default to `track: quick`' so that every spec created by /speckit-specify arrives pre-declared quick. The hard error can then never fire for a newly created spec, and a feature that should be `full` ships declared `quick` unless the author remembers to change it - which is exactly the guess the rule forbids, relocated from the parser to the template.

**Remedy**

> Reconcile the two: either have the template emit a placeholder that fails the check until the author chooses (keeping 'no default' true end to end), or drop the 'no default' framing and state plainly that quick is the seeded value and what prevents a full feature from shipping mis-declared.

### R2-8 — consistency

**Problem**

> The coaching section says 'Offered a one-hour fix and a two-day fix, you took the two-day one', while the plan now totals 'roughly three and a half hours of CC time' excluding step 5 (and the itemised steps sum to 3h15m). A reviewer cannot tell whether the plan shrank, whether 'two-day' meant elapsed calendar time including the user's own decisions, or whether one of the two figures is stale.

**Remedy**

> Use one reconciled framing - for example state that the chosen option is roughly 3.5 hours of CC time plus the user's decisions on steps 5 and 6, which is what 'two-day' referred to - and correct the sum or the rounding so the itemised steps and the total agree.

### R2-9 — clarity

**Problem**

> Assertion 4 is written as 'Every `(NNN)` commit scope maps to a directory that exists', but step 6 explicitly allows the opposite outcome - that 'commit scopes are a separate sequence and should stop wearing three-digit spec numbers' - under which that assertion is the wrong check and would need to become something else (or nothing). The document says the decision 'gates assertion 4' without saying what assertion 4 becomes under each branch. The baseline commit is likewise only described as 'recorded in the test'; no commit, tag or date is named, so the grandfathering boundary is undefined.

**Remedy**

> State what assertion 4 asserts under each outcome of step 6 (including 'this assertion is dropped'), and name the baseline - a specific commit, tag or date - or say that step 6 chooses it and record the rule for choosing.

### R2-10 — clarity

**Problem**

> The error contract covers a missing block, a missing key or an unrecognized value, but the single specified message reads 'declares no valid track (expected quick|full)'. An invalid or missing `status` - which the same rule makes a hard error - would report a track problem, misdirecting whoever has to fix it.

**Remedy**

> Specify a second message for the status case (or a parameterised form naming the offending key and its allowed values), and state that check-prerequisites and the scaffold test emit the same text.

### R2-11 — feasibility

**Problem**

> Step 3 makes the three bash callers hard-error on any spec without valid front matter, and declares a dependency on step 2 (the template) only. Step 4, the backfill that gives the 21 existing directories their front matter, likewise depends only on step 2, so nothing in the stated ordering prevents step 3 from landing first - at which point every existing spec, including whichever one feature.json names, fails check-prerequisites with the new error and main is broken in a second way.

**Remedy**

> Make step 3 depend on step 4 (or state that they must land in a single commit), so the enforcement never precedes the declarations it enforces.

### R2-12 — feasibility

**Problem**

> Assertion 4 is 'skipped when the checkout is shallow ... rather than failing', but CI checkouts are shallow by default, and the document specifies no fetch depth for the workflow. As written the history assertion would skip in every CI run and only ever execute on a developer's full clone, so the commit-scope guard rail does not actually guard the branch. The prior review also asked whether the history assertion runs in every matrix cell or only once; the document answers this only by implication ('Assertions 1 through 3 read files only and run in every matrix cell') and never states where assertion 4 runs.

**Remedy**

> State how CI obtains the history the assertion needs (for example fetch-depth 0, or fetch back to the baseline commit) in the job that runs it, say explicitly in which matrix cell assertion 4 runs, and say whether a skip is reported so a permanently skipped assertion is visible rather than silent.

**R1-3 → R2-12 (persisting)**

> Assertion 4 in step 7 bounds the range with a baseline and skips on a shallow checkout, but the original obligation to specify how the test obtains history in CI and to state whether the history assertion runs in every matrix cell or only once remains unmet: no fetch depth is specified, and the text states only that 'Assertions 1 through 3 ... run in every matrix cell' without saying where assertion 4 runs.
